# [XAS-029] Semantic release via Release Please

**Status**: Open
**Priority**: Medium
**Component**: `release-please-config.json` (new),
`.release-please-manifest.json` (new),
`.github/workflows/release.yml` (new),
`.claude-plugin/marketplace.json`, `CLAUDE.md`, `CONTRIBUTING.md`,
`plugins/*/CHANGELOG.md` (generated)

**Related**: Supersedes [XAS-004b](xas-004b.md), whose bump-script-plus-check
approach is subsumed entirely. Sits under [XAS-004](xas-004.md)'s marketplace
tooling theme but is filed top-level because it replaces rather than extends
that substory.

**Summary**:
As a maintainer, I want plugin versions, tags and changelogs derived from
commit messages, so that releasing stops being a manual double-edit that has
already drifted twice and starts being a consequence of the history.

**Description**:
Versions are bumped by hand today in two files, enforced only by a rule in
`CLAUDE.md`. Nothing derives them, nothing tags them, and there is no changelog.
There are **zero git tags** in the repository.

The absence of tags has a concrete cost. Claude Code resolves versioned plugin
dependencies against tags named `{plugin-name}--v{version}`. Because nobody
tags that way, [XAS-028](xas-028.md) had to declare its `superpowers`
dependency **unversioned** — a constraint would have failed the install with
`no-matching-tag`. Tagging properly is what would let any consumer pin a
version of these plugins.

**Prior art was checked before choosing a tool**, and it changed the answer.
Most marketplaces do not version at all: of 286 plugins in
`claude-plugins-official`, only 14 carry a version in `marketplace.json`, and
all 150 url-sourced and 83 git-subdir entries pin a commit `sha` instead.
Anthropic's own `anthropic-agent-skills` marketplace ships 5 plugins with no
versions. This repository is unusual in maintaining real semver across two
independently versioned plugins, which is why the dual-field sync burden felt
self-inflicted. It largely was.

For repos that do version, the established tool is
[Release Please](https://github.com/googleapis/release-please), with a
documented recipe for Claude plugins. It is path-based, tracks each package
independently, writes changelogs, and runs as a GitHub Action, so no Node
toolchain enters the repo.

**Scope Decisions**:
- **Release Please, not a bespoke script.** The first instinct was to build one
  in `uv`, because the mandatory `{plugin}--v{version}` tag format and
  path-based attribution across two plugins are where off-the-shelf tools are
  usually weakest. That reasoning was wrong: `include-component-in-tag: true`
  with `tag-separator: "--"` produces exactly that format, and per-package
  independent versioning is Release Please's native model rather than a
  bolt-on. Building it would have meant owning release logic to reproduce a
  tool that already fits.
- **Drop `version` from `marketplace.json` entries.** Verified against the
  marketplace schema: *"Plugin version. If set (here **or in `plugin.json`**),
  the plugin is pinned to this string and users only receive updates when it
  changes."* Either location pins it, so `plugin.json` alone preserves update
  detection. Removing the duplicate deletes the sync problem outright rather
  than automating around it, and matches how the wider ecosystem treats the
  marketplace entry: a pointer, not a version record.
- **Attribution by changed path, not by commit scope.** Scopes here are a mix
  of skill names (`refinement`, `naps2-scan`), plugin names (`dev-skills`),
  and non-plugin areas (`backlog`, `tests`, `hooks`, `adr`). `refinement` and
  `naps2-scan` are both skill scopes in *different* plugins, so scope cannot
  determine which plugin to version. A skill-to-plugin map would be a second
  source of truth that goes stale the moment a skill moves. Paths cannot.
- **Release PR, not a direct push to `develop`.** This reverses an earlier
  preference for CI committing back. Release Please's model is a Release PR and
  that is not a config toggle. Accepted: it also restores a review gate on the
  one commit that changes what every consumer receives.
- **A prose change that alters agent behaviour is `feat`, not `docs`.** The
  history already contradicts the standard type-to-bump mapping:
  `docs(dev-skills): document the superpowers dependency` carried a **minor**
  bump, correctly, because it added an instruction to `refinement`. Under
  vanilla rules that commit releases nothing. Rather than customise the
  mapping, adopt the discipline: these plugins are prose, so prose that changes
  what the agent does is a feature. `docs` stays for the backlog, README and
  contributor documentation.
- **Seed the manifest from current versions**, `1.12.0` and `0.2.0`, rather
  than restarting at `1.0.0`. No tags exist to conflict with, and consumers are
  already installed at 1.12.0.

**Acceptance Criteria**:
- [ ] `release-please-config.json` defines both plugins as packages keyed by
      `plugins/<name>`, with `include-component-in-tag: true` and
      `tag-separator: "--"`.
- [ ] `extra-files` updates each `plugin.json` `version` field via JSONPath.
- [ ] `.release-please-manifest.json` seeds `xxthunder-dev-skills` at `1.12.0`
      and `xxthunder-paperless-skills` at `0.2.0`.
- [ ] `.github/workflows/release.yml` runs Release Please on push to `develop`
      with `contents: write`, `pull-requests: write`, `issues: write`.
- [ ] The repository setting *Allow GitHub Actions to create and approve pull
      requests* is enabled, without which the workflow silently cannot open a
      Release PR.
- [ ] `version` is removed from both `marketplace.json` plugin entries, and a
      plugin still updates correctly from a bumped `plugin.json` alone
      (verified with a real `claude plugin update`, not by inspection).
- [ ] A merged Release PR produces tags `xxthunder-dev-skills--v<version>` and
      `xxthunder-paperless-skills--v<version>` in that exact format.
- [ ] A commit touching only one plugin releases only that plugin; a commit
      touching neither (`docs/backlog/`, `tests/`, `.github/`) releases
      nothing.
- [ ] `CHANGELOG.md` is generated per plugin.
- [ ] `CLAUDE.md` and `CONTRIBUTING.md` replace the manual double-bump rule
      with the commit-message contract, including the `feat`-not-`docs` rule
      above.
- [ ] [XAS-004b](xas-004b.md) is closed as superseded, with a note saying why.
- [ ] All existing tests continue to pass.

**Out of scope**:
- GitHub Releases. Tags plus per-plugin changelogs were judged enough; adding
  release notes duplicates the changelog.
- Publishing anywhere but this repository. Consumers install from the
  marketplace pointing at `develop`.
- Versioning the marketplace itself. Only the two plugins are versioned.
- Retroactive tags for past versions. There is no history of releases to
  reconstruct and inventing one would misrepresent when things shipped.

**Open Questions**:
- **Does `claude plugin tag` still validate cleanly once the marketplace entry
  carries no version?** Its documented behaviour is to check that `plugin.json`
  and the enclosing marketplace entry agree. With nothing to agree with, it may
  pass trivially, warn, or refuse. Release Please creates the tags, so this
  only matters if that command is ever used alongside it; worth one check
  rather than an assumption.
- **Does the `develop`-based flow interact badly with Release Please's default
  assumption of a `main` branch?** The workflow takes a target branch, so this
  is expected to be configuration only, but it has not been tried.
