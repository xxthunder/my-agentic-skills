# [XAS-027] Make "the backlog item is the design of record" a plugin-level rule

**Status**: Open
**Priority**: Medium
**Component**: `plugins/xxthunder-dev-skills/hooks/` (new), `plugins/xxthunder-dev-skills/skills/backlog-ops/` (new `design` operation) or a new `design-capture` skill, `plugins/xxthunder-dev-skills/.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`
**Related**: [XAS-025](xas-025.md) — established the backlog conventions and the
`backlog-ops` mechanics skill this builds on. Consumer precedent:
`xxthunder/shortcuts` commit `2e37587` (`docs(process): require a backlog item
before design or implementation (SC-047)`), which encoded the rule in that
repo's `AGENTS.md` — the per-repo duplication this item removes.

**Summary**:
As a maintainer using these skills across several repos, I want the "a backlog
item must exist before design, and the design lives in the item" rule to ship
with the plugin, so that I stop pasting the same paragraph into every repo's
`AGENTS.md` and every repo behaves the same way without per-repo upkeep.

**Description**:
The rule was first written in `xxthunder/shortcuts` as an `AGENTS.md` paragraph.
Repeating that per repo is duplication, drifts as the wording evolves, and only
protects repos someone remembered to edit.

It also **conflicts with `superpowers:brainstorming`**, whose checklist ends by
writing `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` and invoking
`writing-plans`. Left unaddressed, a brainstorming session produces exactly the
duplicate design artifact the rule forbids. This surfaced live in the
`homesmarthome` repo while designing the openHAB config-repo split.

The naive fix — "put it in a skill instead" — does not work on its own:

- **Skills are pull-based.** A skill only shapes behaviour once something
  invokes it, and nothing would invoke a "design goes in the backlog" skill at
  the moment `brainstorming` decides where to write. `AGENTS.md` works because
  it is push-based: always in context.
- **Peer skills have ambiguous precedence.** `using-superpowers` states that
  user instructions (`CLAUDE.md`, `AGENTS.md`, direct requests) override skills,
  but says nothing about one plugin's skill contradicting another's. A
  `xxthunder-dev-skills` skill telling the agent to ignore
  `brainstorming`'s explicit "the terminal state is invoking writing-plans" is
  an argument between peers, not an override.

The mechanism that does generalize is the one `superpowers` uses for its own
always-on rule: a **plugin `SessionStart` hook**. `superpowers` ships
`hooks/hooks.json` with a `startup|clear|compact` matcher that injects
`using-superpowers` into every session without anyone invoking it. This plugin
can ship the same thing.

The design therefore splits along **rule vs mechanics**:

- **A `SessionStart` hook carries the rule** — a few sentences: the backlog item
  is the canonical artifact, it exists before design begins, the design lives in
  the item, standalone design docs are for epics only. Always-on, single source,
  and it arrives in the same context layer as the `superpowers` rule it needs to
  take precedence over.
- **A skill carries the mechanics** — allocate the next ID, render an agreed
  design into the item's sections (Summary / Description / Scope Decisions /
  Acceptance Criteria / UAT), update the README TOC, split into epic +
  substories when the design spans several units of work. Loads on demand, so it
  costs no context until used.

Rule small and always-on; mechanics on demand. Same division `superpowers`
itself uses.

**Scope Decisions**:
- **Hook is guarded on repo shape.** It fires only when the repo actually has a
  backlog (`docs/backlog/README.md` or equivalent), so it stays silent in repos
  that do not use these conventions rather than nagging about a backlog that
  does not exist.
- **The ID prefix is discovered, not configured.** `refinement` already records
  the prefix in the backlog README's Notes section; the hook and skill read it
  from there instead of introducing per-repo hook configuration, which would
  reintroduce the per-repo upkeep this item removes.
- **The hook payload stays short.** It is injected into every session in every
  consuming repo; it states the rule and points at the skill for mechanics
  rather than restating the backlog format.
- **Does not fork or vendor `superpowers`.** The rule redirects where
  `brainstorming`'s output lands; it does not reimplement brainstorming.
- **`AGENTS.md` paragraphs are removed only after the hook is verified** in a
  consuming repo — the per-repo text is the current safety net and stays until
  its replacement demonstrably fires.

**Acceptance Criteria**:
- [ ] `plugins/xxthunder-dev-skills/hooks/hooks.json` exists with a
      `SessionStart` hook (matcher `startup|clear|compact`) that injects the
      backlog-first rule.
- [ ] The hook is a no-op in a repo with no backlog directory (verified in a
      scratch repo).
- [ ] The injected text states: the backlog item is the canonical artifact; it
      must exist before design; the design lives in the item; standalone design
      docs are reserved for epics and linked, not duplicated.
- [ ] Design-capture mechanics exist — either a new `design` operation on
      `backlog-ops` or a new `design-capture` skill (decide during
      implementation; see Open Questions) — that turns an agreed design into a
      correctly formatted item, allocates the next ID, and updates the README
      TOC.
- [ ] Mechanics handle the epic case: a design spanning several units of work
      becomes a parent item plus letter-suffixed substories, per XAS-025.
- [ ] Consistent with `backlog-ops`: stages file edits only, never commits.
- [ ] `plugin.json` and `marketplace.json` versions bumped (minor — new
      behaviour and a new hook).
- [ ] Verified end-to-end in a consuming repo: start a session, confirm the rule
      is present without invoking anything, run a brainstorming session, and
      confirm the design lands as a backlog item rather than a `specs/` file.
- [ ] The `AGENTS.md` paragraph in `xxthunder/shortcuts` is removed once the
      hook is verified, with the repo left relying on the plugin.

**Out of scope**:
- Changing `superpowers` itself, or forking `brainstorming` / `writing-plans`.
- Migrating existing `docs/superpowers/specs/` documents in consuming repos into
  backlog items.
- Any non-Claude agent target — hooks are Claude Code-specific, so this rule does
  not carry to the multi-agent work in [XAS-003](xas-003.md).

**Open Questions**:
- **New skill or a `backlog-ops` operation?** `backlog-ops` is deliberately
  scoped to *mechanical lifecycle* operations (pull / check / complete), and
  authoring a design is a different kind of act — it has judgement in it. A
  separate `design-capture` skill keeps that boundary clean; an added operation
  keeps all backlog writing in one place. Decide during implementation.
- **Does hook-injected text reliably outrank a peer plugin's skill instruction?**
  The reasoning here is that it arrives as session context rather than as a
  skill, which is how `superpowers` gets its own rule to stick — but this should
  be confirmed by observation during the end-to-end verification, not assumed.
- **Interaction with `brainstorming`'s terminal state.** That skill explicitly
  ends by invoking `writing-plans`. Whether the rule should also redirect the
  *plan* into the item (acceptance criteria are arguably the plan) or leave
  plans alone is unresolved.
