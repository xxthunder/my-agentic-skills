**Summary**:
As a maintainer running several repos with coding agents, I want the record of
how a repo is built and why — its architecture and the decisions behind it —
created and
maintained by the plugin, so that every repo carries a human-readable account of
why it looks the way it does, and every session starts already knowing it.

**Description**:
Today a repo's design exists in three unsatisfying places: inside closed backlog
items, inside the head of whoever made the call, and inside `AGENTS.md`
paragraphs pasted from repo to repo. None of them survives well. The backlog
item closes. Memory fades. The pasted paragraph drifts the moment its wording
changes anywhere else.

`superpowers:brainstorming` makes this worse rather than better: its checklist
ends by writing `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, a
per-story spec that duplicates the backlog item that should already hold that
design. This surfaced live in the `homesmarthome` repo while designing the
openHAB config-repo split.

The framing that resolves it is **lifetime, not item size**. A.SPICE and the
V-Model organise artifacts by abstraction level and they describe *the product*,
so they live as long as it does. Scrum organises by increment of value and
describes *a change to the product*, so its artifacts stop being maintained at
Done. Asking "should the design live in the epic, the story, or a document?"
mixes the two axes, which is why it has no answer. Split by lifetime and it
does:

| What it describes                       | Lives where       | Lifetime                     |
|-----------------------------------------|-------------------|------------------------------|
| The work — what changes, why now, done-when | Story / Epic  | Kept current until Done, then history |
| The product's structure                 | `architecture.md` | As long as the product       |
| Why a structural choice was made        | ADR               | Forever; superseded, not edited |
| How the code actually works             | Code + tests      | The only artifact that cannot lie |

Nothing here is ever deleted. A closed backlog item stays in the repo and is a
true account of the change it describes. What ends at Done is its authority
about the *present*: nothing keeps it current afterwards, so it is history
rather than reference. Design that still constrains the repo has to be lifted
into the record before the item closes — see [XAS-027j](xas-027j.md).

So the plugin gains exactly two artifacts that stay binding on the present — an
ADR log and a living
`architecture.md` — and no third place for design to hide. Work-level design
stays in the item's `Scope Decisions`; decomposition stays in the epic. See
[ADR-0001](../adr/0001-two-design-artifacts-split-by-lifetime.md).

The backlog already builds half a V-Model without anyone noticing: a story's
Summary and Description are its requirement, and its Acceptance Criteria and UAT
blocks in the same file are that requirement's verification mirror. What is
missing is only the middle band — architecture and its rationale — plus the idea
that integration tests verify the architecture the way unit tests verify code.

Four components deliver it:

- **`design-record`** ([027a](xas-027a.md), [027b](xas-027b.md)) — the only
  writer of the record. Drafts ADRs, edits `architecture.md` sections and their
  diagrams, maintains the ADR index. Stages edits, never commits.
- **`architecture-scan`** ([027d](xas-027d.md)) — read-only. Derives the real
  structure from the repo and diffs it against `architecture.md`. Empty doc →
  bootstrap proposal; populated doc → drift report.
- **A `SessionStart` hook** ([027c](xas-027c.md)) — orientation. States what
  record exists *in this repo* and who writes it. Guarded on repo shape, silent
  elsewhere.
- **Wire-up** ([027e](xas-027e.md)) — `refinement`, `tdd-workflow` and
  `commit-helper` point at `design-record` at the moments that produce record
  changes. They suggest; none of them blocks.

**Scope Decisions**:
- **Two artifacts that stay binding on the present, split by lifetime** — ADR log plus living
  `architecture.md`; no per-epic design docs and no standing requirements
  document. [ADR-0001](../adr/0001-two-design-artifacts-split-by-lifetime.md)
- **`architecture.md` uses fixed slots for structure, free-form for behaviour** —
  so a structural update is an edit to a known diagram rather than another
  diagram appended. [ADR-0002](../adr/0002-architecture-doc-fixed-slots-for-structure.md)
- **The record has exactly one writer** — `design-record` writes,
  `architecture-scan` proposes. [ADR-0003](../adr/0003-one-writer-for-the-design-record.md)
- **The always-on rule is orientation, not enforcement** — the hook says where
  the record lives; it does not gate work.
  [ADR-0004](../adr/0004-always-on-rule-is-orientation-not-enforcement.md)
- **Bootstrap architecture from code; never reconstruct ADRs** — rationale is
  not recoverable from code, so an inferred ADR is fiction.
  [ADR-0005](../adr/0005-bootstrap-architecture-never-reconstruct-adrs.md)
- **`design-record` authors prose, unlike `backlog-ops`.** A deliberate
  divergence from the mechanics-only contract, so that recording a decision is
  one invocation rather than two. The skill must state the divergence and its
  reason, or a future session will "fix" the inconsistency and break it.
- **Plans are a task breakdown, and are deleted once their work lands.**
  `superpowers:writing-plans` output is a working document, so by the rule above
  it is not part of the record: a plan stops binding once its work lands.
  Two constraints follow, and the first was learned the hard way. A plan that
  reproduces the design — or carries the finished text of the files it is
  planning — is a spec under another name, and belongs in the backlog item. The
  plan written for [XAS-027a](xas-027a.md) and [XAS-027b](xas-027b.md) was 743
  lines, 64% of it inside code fences holding the complete text of three files
  that then shipped. It duplicated the items it was planning from, and drifted
  from them: it was the last place in the repo still saying "dies at Done" after
  [XAS-027j](xas-027j.md) corrected that wording everywhere else.
  Second: a plan is deleted when its stories close. Leaving it is how a working
  document becomes a second, stale account of a design nobody is maintaining.
  That plan has been deleted; `docs/superpowers/` no longer exists here.
- **ID prefix and record paths are discovered, not configured** — the prefix
  comes from the backlog README's Notes section, the paths from the repo. No
  per-repo hook configuration, which would reintroduce the per-repo upkeep this
  epic removes.

**Acceptance Criteria**:
- [ ] End-to-end in a consuming repo: a fresh session is oriented without
      anything being invoked, and a brainstorming session's output lands as a
      backlog item plus an ADR rather than a `docs/superpowers/specs/` file.
- [ ] This repo carries its own `architecture.md`, produced through the skills;
      and ADRs `0001`–`0005`, written by hand before the skills existed, have
      been reconciled against what the skills now produce.
- [ ] No repo needs an `AGENTS.md` paragraph to get the *design-location*
      behaviour. Enforcement is explicitly out of scope: a repo wanting a
      "backlog item MUST exist first" gate still states that locally, which
      follows from [ADR-0004](../adr/0004-always-on-rule-is-orientation-not-enforcement.md)
      rather than being a shortfall. Qualified while running
      [XAS-027g](xas-027g.md), where the distinction first became visible.
- [ ] `plugin.json` and `marketplace.json` versions agree after every substory
      that touches the plugin.

**Out of scope**:
- Changing `superpowers` itself, or forking `brainstorming` / `writing-plans`.
- Migrating existing `docs/superpowers/specs/` documents in consuming repos into
  backlog items or ADRs.
- Traceability machinery — trace matrices, bidirectional link validation, work
  product IDs. A.SPICE's evidence apparatus exists to survive an audit; these
  are single-maintainer repos with no audit. The shape is worth taking, the
  machinery is not.
- Any non-Claude agent target — hooks are Claude Code-specific, so the hook does
  not carry to the multi-agent work in [XAS-003](xas-003.md). The two skills do.

**Open Questions**:
- **Does hook-injected text reliably outrank a peer plugin's skill instruction?**
  The reasoning is that it arrives as session context rather than as a skill,
  which is how `superpowers` makes its own rule stick. The mitigation is that the
  payload names the competing step directly rather than stating a general rule.
  To be confirmed by observation in [XAS-027g](xas-027g.md), not assumed.
- **How much rationale can `design-record` actually source from a conversation?**
  If it turns out to ask for nearly every field, the entry cost may be high
  enough to discourage recording decisions at all — which would argue for a
  shorter ADR template rather than a more persistent skill.
