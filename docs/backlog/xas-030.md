# [XAS-030] ✅ DONE - Remove `tdd-workflow`

**Status**: Done (2026-08-22)
**Priority**: Medium
**Component**: `plugins/xxthunder-dev-skills/skills/tdd-workflow/` (removed),
`plugins/xxthunder-dev-skills/skills/backlog-ops/SKILL.md`,
`plugins/xxthunder-dev-skills/.claude-plugin/plugin.json`,
`.claude-plugin/marketplace.json`, `README.md`, `docs/architecture.md`

**Related**: [XAS-028](xas-028.md) declared the `superpowers` dependency and
added the section in which `tdd-workflow` concedes the overlap.
[XAS-027e](xas-027e.md) wired the design-record suggestion into both
`tdd-workflow` and `commit-helper`; only the second is kept.

**Summary**:
As a maintainer, I want `tdd-workflow` removed, so that the plugin stops
shipping a large inferior copy of a skill it already depends on.

**Description**:
`tdd-workflow` is 172 lines. **122 of them — 75% — are Red-Green-Refactor
cycle content that `superpowers:test-driven-development` already covers**, in
320 lines and in more depth: an Iron Law, explicit Verify-RED and Verify-GREEN
steps, a rationalizations table, red flags, a worked bug-fix example and a
verification checklist. Ours has none of those.

The skill already concedes this. XAS-028 added a section saying: *"follow the
superpowers skill for the cycle and this one for the boundaries. Do not run two
separate cycles."* So it carries 122 lines it explicitly instructs the reader
not to use.

That leaves 40 lines of integration, and each part is already covered
elsewhere:

- **The design-record suggestion on a boundary move** is item 4 of
  `commit-helper`'s Pre-Commit Checklist, added by the same story
  ([XAS-027e](xas-027e.md)). `commit-helper` fires on every commit, whereas
  `tdd-workflow` fires only at the end of a cycle someone chose to run — strictly
  better coverage from the copy being kept.
- **Backlog transitions at cycle boundaries** are `backlog-ops`' own documented
  triggers: "start XAS-025", "close XAS-025", "tick AC 2 on XAS-025". Those are
  user-driven and need no TDD skill to fire.
- **"Integration with Test Execution Skill"** points at "the project's test
  execution skill", which is not a thing that exists in this marketplace.

**Scope Decisions**:
- **Removed, not trimmed.** A trimmed boundary-only skill would still have to
  *trigger during TDD*, putting its description in direct competition with
  `superpowers:test-driven-development` for "implementing a feature". Two skills
  racing on one trigger is the ambiguity
  [ADR-0004](../adr/0004-always-on-rule-is-orientation-not-enforcement.md)
  already had to reason about once, and the prize here is 40 lines that are
  redundant anyway.
- **Nothing moves into the `SessionStart` hook.** It would fit the hook's
  always-on shape, but ADR-0004 records that hooks are Claude Code-specific
  while skills port, and [XAS-003](xas-003.md) plans other agent targets.
  Putting workflow guidance in the hook would quietly make it Claude-only.
- **This is a breaking change: 1.14.0 → 2.0.0.** `tdd-workflow` is
  `user_invocable`, so `/xxthunder-dev-skills:tdd-workflow` stops resolving for
  anyone who uses it. Semver says major, and calling it minor because the
  replacement is a peer plugin's skill would be dishonest about what an
  installer experiences.
- **XAS-027e is not reopened.** Its acceptance criterion that `tdd-workflow`
  suggests `design-record` at cycle end was met when written. That delivery is
  superseded here rather than retracted, and the item is annotated so a reader
  is not left wondering where the skill went.

**Follow-up applied in this item** (2026-08-22): removing the skill removed two
different things, and only one was duplicated.

The *technique* was duplicated and superpowers covers it better. The
*expectation* — that this repo practises TDD at all — was not duplicated
anywhere, and `CLAUDE.md` never stated it. The skill had been carrying it
silently, and deleting the skill deleted it.

Worse, a skill was the wrong carrier regardless. Both TDD skills trigger on a
*state* ("implementing a feature"), not a phrase, so both depend on the model
noticing. Three TDD cycles ran during XAS-027c, XAS-027h and XAS-027i in this
repository and `superpowers:test-driven-development` was invoked in none of
them. A convention has to be present before implementation starts, which means
push-based context, not a pull-based skill.

So the convention moved to `CLAUDE.md` as a Key Rule — always in context,
pointing at `superpowers:test-driven-development` for the cycle rather than
restating it, per [XAS-027k](xas-027k.md). `commit-helper` carries the shipped
form for consuming repos and names its own limitation: it states the
expectation at commit time, which is the last possible moment rather than the
right one.

Two stale `tdd-workflow` references in `CLAUDE.md` were fixed at the same time
— a plugin listing and a commit-scope example.
