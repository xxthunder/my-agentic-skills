# [XAS-032] Establish whether `retrospective` triggers in practice

**Status**: Open
**Priority**: Low
**Component**: `plugins/xxthunder-dev-skills/skills/retrospective/SKILL.md`

**Related**: Found reviewing all dev skills alongside [XAS-030](xas-030.md).
Unlike that item this is a question, not a defect: nothing here is duplicated
and nothing is wrong.

**Summary**:
As a maintainer, I want to know whether `retrospective` fires when it should,
so that a 228-line skill is either earning its place or knowingly kept for a
reason other than use.

**Description**:
`retrospective` is the second-largest skill in the plugin at 228 lines, behind
`commit-helper`. It duplicates nothing in `superpowers` — `receiving-code-review`
is about evaluating feedback, not about capturing an incident and updating
project guidelines. Its content is sound: five workflow steps, a root-cause
category taxonomy, two worked examples, and a file decision matrix.

The open question is whether it ever runs. Its trigger list is *"I am not
happy", "this is not what I wanted", "you shouldn't have done that", "that's
wrong", "this is incorrect"*, plus a "why did you X?" asked in a corrective
tone — with an explicit instruction not to fire on neutral curiosity.

During the long session that produced XAS-027 and its substories, the user
corrected the agent repeatedly and pointedly: an imprecise term challenged with
"BE MORE PRECISE!", a mis-scoped reference challenged with "What are you
talking about?", an unwanted artifact challenged with "This is exactly what I
wanted to avoid". Several of those are close in shape to the documented
triggers. The skill fired **zero** times.

That does not mean it is broken. Three readings fit and they lead to different
outcomes:

1. The triggers are too literal — real dissatisfaction rarely uses those exact
   phrases, and the tone condition is doing work the model cannot judge
   reliably.
2. It fired correctly by not firing — those corrections were resolved inline
   and a formal retrospective would have been ceremony.
3. It is competing with the corrections themselves: by the time the user has
   said what is wrong, fixing it is more useful than analysing why.

**Scope Decisions**:
- **Investigate before changing anything.** This item exists to answer a
  question. Rewriting the triggers first would be guessing.
- **Deletion is a permitted outcome.** If the honest answer is that in-line
  correction always beats a formal retrospective, that is worth knowing and
  acting on rather than keeping 228 lines out of politeness.
- **So is doing nothing.** A skill that fires rarely but valuably is fine; the
  point is to decide knowingly.

**Acceptance Criteria**:
- [ ] The three readings above are tested against real transcript evidence, not
      argued from the skill text.
- [ ] A decision is recorded: keep as-is, retrigger, shrink, or remove — with
      the reasoning.
- [ ] If the triggers change, the new ones are drawn from language users
      actually used, not invented.
- [ ] If the outcome is removal, the same check as [XAS-030](xas-030.md) is
      applied first: what does this skill carry that nothing else does, and
      where does that go?

**Out of scope**:
- Rewriting the retrospective workflow itself. Its five steps are not in
  question.
- Any other skill's triggers.
