# [XAS-021] Persist `naps2-scan` session settings across invocations

**Status**: Done
**Priority**: Medium
**Epic**: XAS-015
**Component**: plugins/xxthunder-paperless-skills/skills/naps2-scan/

**Summary**:
As a user who runs `naps2-scan` regularly, I want the skill to remember my NAPS2 executable path and preferred profile so that I'm not asked the same questions on every scan session.

**Description**:
Currently `naps2-scan` asks for the NAPS2 executable path (when not on `PATH`), profile name, and OCR language every session. The first two rarely change for a given user — storing them in a per-user config and reusing across invocations would make repeated scans friction-free.

**Proposed design**:
- Config location: `%APPDATA%\naps2-scan\config.json` on Windows, `~/.config/naps2-scan/config.json` on Linux/macOS (follow XDG where applicable).
- Schema (keep minimal):
  ```json
  {
    "exe_path": "C:\\Users\\karst\\scoop\\apps\\naps2\\current\\App\\NAPS2.Console.exe",
    "default_profile": "MFC Flachbett",
    "default_ocr_lang": "eng+deu"
  }
  ```
- Skill behaviour:
  - On start, read config. If present, use values as defaults.
  - Only ask for values that are missing or fail validation (e.g., `exe_path` no longer exists).
  - After a successful scan, write back any newly-supplied values.
  - User can edit or delete the file to reset.
- OCR language remains per-invocation overridable even when a default is stored.

**Scope Decisions**:
- Config is per-user, not per-repository — it's local state, not portable skill content.
- No encryption / no secrets — paths and profile names only.
- Skill must not fail if the config directory cannot be created; it degrades to "ask every time".
- **Broadened scope**: this story also migrates all Python touchpoints in `naps2-scan` (config read/write + PDF text extraction) to `uv run` scripts with [PEP 723](https://peps.python.org/pep-0723/) inline dependency metadata, shipped under `scripts/` next to `SKILL.md`. Rationale: the config work introduces two new Python call sites, and inlining them as `python -c` one-liners is fragile (Windows quoting, no deps declaration). Consolidating on `uv`-run scripts gives self-bootstrapping dependency management (`pypdf` no longer a manual prereq), robust file-based code, and a single invocation pattern. Trade-off: `uv` becomes a skill prerequisite (cheap to install; see `SKILL.md`).
- Upgrade `PyPDF2` → `pypdf` (PyPDF2 is the deprecated upstream name) as part of the extraction-script migration.

**Open questions**:
- Should we persist the last-used output directory too, or is current-working-directory always right? (Current-dir is simpler and already matches user expectation.)
- Multi-profile users: do we need a named-set concept (e.g., "home", "office"), or is a single default enough? Start with single default; revisit if needed.

**Dependencies**:
- XAS-018 (naps2-scan skill base)

**Acceptance Criteria**:
- [x] Config file location and schema documented in `SKILL.md`
- [x] Skill reads config on start and uses values as defaults
- [x] Skill writes values back after the user supplies them (on successful scan)
- [x] Skill still works if config file is absent or unreadable (falls back to asking)
